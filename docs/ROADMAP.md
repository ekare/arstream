### M6 in detail

**JNI bootstrap** (`mobile/android/plugins/jni_bootstrap/`) — a standalone Gradle module (Kotlin, `GodotPlugin` v2) that hands the `JNIEnv*`/`Activity` to native code exactly once. Three non-obvious bugs found and fixed along the way, all now captured as comments at the fix site:
- `onGodotMainLoopStarted()` — despite looking like an Activity lifecycle callback — runs on Godot's own engine thread, **not** the Android UI thread. Confirmed on-device: calling ARCore's async availability check directly from there aborts (`SIGABRT` inside `libarcore_sdk_c.so`); fixed by wrapping the call in `Activity.runOnUiThread{}`.
- The GDExtension `.so` is packaged with a platform/target/arch-suffixed filename (`libarcapture.android.template_debug.arm64.so`, from Godot's own SCons build), not a plain `libarcapture.so` — `System.loadLibrary("arcapture")` failed until the plugin discovered the real filename from the APK's own zip entries at runtime and loaded that.
- ARCore's C API calls back into ARCore's own **Java** classes internally — omitting `com.google.ar:core` as a real Gradle dependency (only vendoring the raw `.so`+header) crashed under `-Xcheck:jni`. Fixed by declaring it via `EditorExportPlugin._get_android_dependencies()` (`mobile/addons/jni_bootstrap/export_plugin.gd`) so Godot's own Gradle build resolves it — a locally-built `.aar` has no `pom.xml` for transitive dependencies to be inferred from.

**ARCore availability check** — `arcore_availability.h/.cpp` wraps `ArCoreApk_checkAvailabilityAsync`, caches the last result, triggered once at startup from the JNI bootstrap plugin. Verified on the A30s: **`SUPPORTED_INSTALLED`** — the community assumption noted in `DEVICE_COMPATIBILITY.md` ("A30s probably isn't ARCore-certified") turned out to be wrong for this specific unit.

**`ArCoreCaptureSession` + `GlBlitRenderer`** (`capture/android/`) — owns the `ArSession` and a dedicated render thread that drives `ArSession_update()`, extracts pose/point-cloud/intrinsics, and blits ARCore's `GL_TEXTURE_EXTERNAL_OES` camera texture into the encoder's `Surface` via a minimal EGL/GLES2 helper (ARCore has no zero-copy Surface-write path the way Camera2 does). Two bugs found and fixed on-device:
- `AR_ERROR_MISSING_GL_CONTEXT` — the EGL context was created on the thread that called `start()`, but `ArSession_update()` ran on a separate render thread (EGL contexts are per-thread). Fixed by moving ALL GL/EGL setup + `ArSession_resume()` inside the render thread itself, reporting success/failure back to the caller synchronously via `std::promise`/`std::future`.
- Aspect-ratio mismatch — ARCore's own default camera config (640×480, 4:3) didn't match the encoder's requested resolution (1280×720, 16:9), stretching the blitted image. Fixed with `ArSession_setCameraConfig`, picking the supported config whose aspect ratio (then pixel count) is closest to the encoder's target.

**`CaptureController::decide_backend()`** — real runtime dispatch, no longer hardcoded to Camera2. Reads the *cached* availability result (not re-queried per capture start, since the check needs the UI thread and `start_capture()` doesn't run on it) plus a `debug.arstream.capture_backend` Android system property (`adb shell setprop debug.arstream.capture_backend arcore|camera2`) for forcing a specific backend during testing — persists across app restarts, unlike an in-memory flag. In `auto` (the property unset), a failing ArCore session falls back to Camera2 silently; a forced backend fails loudly instead (no silent fallback).

**End-to-end device verification** (A30s, `arcore` backend forced): 900 frames @ 29.4fps real-time H.264 encode through the ARCore→GL→encoder path; `poses.jsonl` showed a realistic `PAUSED`→`TRACKING` transition; `intrinsics.json` reported sane focal length/principal point matching the encoder's 1280×720 after the aspect-ratio fix; `imu.jsonl` populated independently of the backend (as required). **Not yet verified by a human physically moving the phone** (this test was driven entirely over ADB, phone stationary on a desk): `points.jsonl` came back empty, plausibly because ARCore's sparse feature point cloud needs camera parallax to populate — expected behavior for a motionless camera, but not distinguished from a bug by this test alone. Frame orientation also wasn't conclusively confirmed visually (the camera was pointed at a dim, texture-poor surface).

## Deferred (v2 / next phase, not being built now)

- **iOS/ARKit support** — via an `.mm` (Objective-C++) bridge: `arkit_capture_session.mm`, `avf_capture_session.mm`, `imu_sampler_ios.mm`. No Mac and no test device yet. See [`docs/IOS_HANDOVER.md`](IOS_HANDOVER.md) for where to start once a Mac is available, which files can be reused unchanged (protocol, `StreamSink`, `StreamClient` — all already platform-independent), and the open unknowns. `stream_client.cpp`'s POSIX socket code has already been opened up for `IOS_ENABLED` too (verified via the Android build; it needed nothing iOS-specific).
- **v2 transport layer: UDP + lightweight/fast encryption** — the same message format over UDP (the `sequence_number` field in the header is already reserved for this), with loss/ordering handled manually; needed once NAT-behind/lossy internet connections and TCP's head-of-line blocking start affecting video latency. Encryption should be a low-latency scheme instead of full TLS — a lightweight handshake + ChaCha20-Poly1305 (or a similar AEAD) — not yet designed, just noted as a direction. QUIC (UDP+TLS1.3 already combined) is also a candidate that solves both problems in one step.
- **v1's current boundary** — TCP-only, no TLS/authentication, assumes a trusted network (see `PROTOCOL.md` §6). Recommendation until this is addressed: a WireGuard/Tailscale/SSH tunnel instead of bolting crypto onto the protocol.
- **32-bit (`armv7`) target build** — could be considered for very old devices; the A30s is already arm64, not a priority.
- **Software H.264 encoder fallback** — a device with no hardware AVC encoder is considered rare; will be addressed if one actually turns up.
